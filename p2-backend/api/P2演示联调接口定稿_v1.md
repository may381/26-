# P2 演示联调接口定稿 v1.1

2026-11-07。游览状态由 V20 迁移保存，合成音频由 V21 迁移保存。HTTPS 联调域名由部署环境配置。

## 通用约定

- 路径统一以 `/api/v3` 开头。本人操作沿用现有身份校验，`userId` 示例为 `u100`，成功返回 HTTP 200 和 `{code,message,data}`。时间字段为带时区的 ISO 8601。
- 游览沿用现有字段 `estimatedFinishAt` 和 `remainingSpotIds`。剩余站点按当前路线顺序返回，排除已到访和已跳过的站点。前端按 ID 补齐站名。
- 旧客户端上报进度时仍可携带 ISO 8601 格式的 `estimatedFinishAt`，包括已经过去的时间。响应中的 ETA 由 P2 计算。新客户端可省略这个请求字段。
- 新增 `tripVersion`，由后端在进度、改线、跳站、休息、结束游览提交成功后递增。新增跳站、休息写接口传 `expectedTripVersion` 和 `Idempotency-Key`。同一操作重试沿用原 Key 和正文，返回第一次提交的响应。要读取最新状态可重新查询。版本冲突返回 409，前端重新查询后再由用户决定是否提交。

## 1. 恢复进行中的游览

查询成功时返回下方的完整行程视图。前端使用 `data.id` 恢复游览，用 `data.startedAt` 恢复计时。创建、详情和恢复返回同一个服务端开始时间。新建游览的 `tripVersion` 为 1，后续操作使用最新响应中的版本。

`GET /api/v3/trips/active?userId=u100`。没有进行中的游览时返回：

```json
{"code":"OK","message":"成功","data":null}
```

有游览时返回如下，`id` 即 `tripId`。同样的行程状态字段也会补到 `GET /api/v3/trips/{id}?userId=u100` 的现有详情响应。

```json
{
  "code":"OK","message":"成功",
  "data":{
    "id":"TRIP_ID","userId":"u100","routeId":"r1","status":"ACTIVE",
    "startedAt":"2026-11-06T15:30:00+08:00","tripVersion":8,"progressSeq":3,"currentSpotId":"spot-002",
    "visitedSpotIds":["spot-001"],"skippedSpotIds":[],
    "remainingSpotIds":["spot-002","spot-003"],
    "estimatedFinishAt":"2026-11-06T16:30:00+08:00",
    "activeRest":null
  }
}
```

## 2. 到站和跳站

旧版进度请求仍可带合法 ISO 8601 格式的 stimatedFinishAt，过去时间也可提交。进度响应和行程视图中的 ETA 由 P2 计算。新客户端可省略请求字段。

到站复用 `POST /api/v3/trips/{id}/progress?userId=u100`。继续按现有契约提交 `progressSeq`、`currentSpotId`、`visitedSpotIds` 等字段。到站或整条改线成功后，重新查行程详情获取最新 `tripVersion`、剩余站点和预计结束时间，再发起需要版本的操作。旧版客户端上报的时间不覆盖行程视图中的计算结果。

跳站使用 `POST /api/v3/trips/{id}/stops/{spotId}/skip?userId=u100`，请求头带 `Idempotency-Key`。

```json
{"expectedTripVersion":8}
```

只能跳过当前路线中尚未到访、尚未跳过的站点。跳过当前站后，当前站指针移到第一个剩余站点，该站仍需用户上报到访。剩余站点为空时保持游览进行中，结束游览仍由用户发起。改线时保留已跳过记录，对新路线按同一套规则计算剩余站点。

示例响应的 `data` 与恢复接口使用同一结构，主要变化如下。

```json
{
  "tripVersion":9,"currentSpotId":"spot-003",
  "skippedSpotIds":["spot-002"],"remainingSpotIds":["spot-003"],
  "estimatedFinishAt":"2026-11-06T16:20:00+08:00"
}
```

## 3. 独立休息事件

一次游览最多有一个进行中的休息。休息事件有自己的 ID，不占用景点序号，也不写入到访或跳过列表。以下三个操作均返回更新后的行程状态，包含最新 `activeRest`、`tripVersion` 和 `estimatedFinishAt`。

| 请求 | 示例正文 |
|---|---|
| POST /api/v3/trips/{id}/rests?userId=u100 | `{"expectedTripVersion":9,"plannedMinutes":10,"facilityId":null,"location":{"lat":22.581,"lng":114.0608,"coordinateSystem":"GCJ-02"}}` |
| PATCH /api/v3/trips/{id}/rests/{restId}?userId=u100 | `{"expectedTripVersion":10,"additionalMinutes":5}` |
| POST /api/v3/trips/{id}/rests/{restId}/finish?userId=u100 | `{"expectedTripVersion":11}` |

`facilityId` 可为空，提供时须属于当前游览景区。地图标点使用 `location`，坐标系必填，可传 `GCJ-02` 或 `WGS84`。开始时间由服务端生成，单次休息总计划时长为 1～1440 分钟。

```json
{
  "id":"REST_ID","status":"RESTING",
  "restStartedAt":"2026-11-06T15:40:00+08:00",
  "plannedMinutes":10,"facilityId":null,
  "location":{"lat":22.581,"lng":114.0608,"coordinateSystem":"GCJ-02"},
  "restEndedAt":null
}
```

结束后状态为 `FINISHED`，填写 `restEndedAt`，行程状态中的 `activeRest` 清空。增加 `GET /api/v3/trips/{id}/rests?userId=u100` 读取休息事件列表，供刷新后恢复行程展示。计划时间到达后由用户结束休息。结束整个游览时，后端同时结束仍在进行的休息。

行程视图的 ETA 使用现有路线中通往剩余站点的分段步行分钟数，加上最近一次行程更新后尚需计入的休息时长。开始时计入计划休息，延长只增加新增分钟，结束后以实际时长替代原计划。跳站后沿用路线分段时长估算。到站仍走现有进度接口，前端以行程详情或恢复接口中的 ETA 为准。

## 4. HTTPS 签名媒体

用 `POST /api/v3/trips/{id}/attachments?userId=u100` 上传照片，正文为 multipart，字段名是 `file`。上传响应的 `data` 和 `GET /api/v3/travel-records/{id}?userId=u100` 返回的 `data.media[]` 都包含 `url` 和 `expiresAt`。本人签名 URL 有效期最多 15 分钟，可以直接给图片组件使用。照片链接过期后重新查询游后记录详情。

```json
{
  "id":"MEDIA_ID","mimeType":"image/jpeg",
  "url":"https://api.example.com/api/v3/media/signed/MEDIA_ID?kind=TRIP&exp=UNIX_SECONDS&sig=SIGNATURE",
  "expiresAt":"2026-11-06T16:15:00+08:00"
}
```

- 签发时校验调用者有权读取媒体。读取时验证签名、过期时间和媒体状态，浏览器或客户端无需附加身份头。签名绑定资源和过期时间，过期或签名无效返回 403。
- 私有签名直链继续采用 `Cache-Control: no-store`。小程序以实际 HTTPS 联调域名和对应请求／下载配置做真机验收。部署时设置 `MEDIA_PUBLIC_ORIGIN`（HTTPS 域名）和 `MEDIA_SIGNING_KEY`（至少 32 字节随机数据的 Base64）。本地未设置域名时，返回相对 URL，前端用 P2 的地址解析。
- 分享页继续走 `/api/v3/travel-record-shares/{shareId}/media/{mediaId}`。每次读取校验分享状态和媒体范围，过期或撤销后返回 404。媒体可访问期随该分享链接的 7 天有效期及撤销状态。

## 5. 真实语音

保持现有两个入口。启动本地语音服务后，为 P2 配置 `SPEECH_MODE=http` 和 `SPEECH_SERVICE_URL=http://127.0.0.1:18010`。语音请求由 P2 直接转发给语音服务。

本地从仓库根目录打开两个 PowerShell 窗口。第一个窗口运行语音服务，第二个运行 P2。

```powershell
# 第一个窗口
pwsh -NoProfile -File .\p2-backend\speech\start-local.ps1

# 第二个窗口
$env:SPEECH_MODE = 'http'
pwsh -NoProfile -File .\p2-backend\scripts\dev.ps1
```

- `POST /api/v3/speech/transcriptions?userId=u100`，multipart 字段 `audio`。成功示例为 `{"code":"OK","message":"成功","data":{"text":"我想找附近的休息座椅。"}}`。
- `POST /api/v3/speech/syntheses?userId=u100`，正文 `{"text":"前方有休息座椅。","speechRate":0.9}`，成功返回如下。保留现有 `audioUrl`，沿用照片的签名与过期规则。

```json
{
  "code":"OK","message":"成功",
  "data":{
    "id":"AUDIO_ID","mimeType":"audio/wav",
    "audioUrl":"https://api.example.com/api/v3/media/signed/AUDIO_ID?kind=SPEECH&exp=UNIX_SECONDS&sig=SIGNATURE",
    "expiresAt":"2026-11-06T16:15:00+08:00"
  }
}
```

增加 `GET /api/v3/speech/syntheses/{audioId}?userId=u100`，本人可在音频保留期间获取新链接。音频保留 24 小时，清理后返回 404，再按需重新合成。语音服务不可用时返回可识别的错误，前端保留文本交互。

## 6. 地图与联调验收

旧版本操作返回 HTTP 409：

```json
{"code":"CONFLICT","message":"游览状态已更新，请刷新后重试","data":null}
```

媒体链接返回 403 后，前端按媒体类型重新获取一次地址。如果重新获取也被拒绝，显示媒体不可用。

继续使用 `GET /api/v3/routes/{id}/map`。本地实测路线 `r1` 返回 HTTP 200，`source=MOCK`、`provider=AMAP`、`coordinateSystem=GCJ-02`。景点是演示点位，步行路径由高德计算。前端可用 GCJ-02 坐标绘制地图，页面标注演示路线。缺少高德 Web 服务 Key 时返回 HTTP 502。

验收主线：创建游览 → 上报到站 → 跳过一站 → 开始并延长休息 → 换端恢复 → 结束休息 → 结束游览 → 上传照片 → 三端显示。另测本人 URL 过期后刷新、其他用户不能签发本人媒体链接、分享撤销后媒体失效、语音识别和合成播放。
