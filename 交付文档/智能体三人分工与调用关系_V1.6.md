# 智能体三人分工与调用关系

V1.6 纯文本与表格版｜2026-10-29

> 三个人共用学校模型，各自开发模块；用户只面对A1 总智能体。当前v2.0继续使用，v3.0 r1仍是待确认草案，下面说明目标协作关系，不表示新接口已经上线。

## 1. 统一约定：先分清两个“调用”

| 调用什么 | 是什么意思 |
|---|---|
| 学校模型 qwen3.8-27b | 三人的程序都可以调用，获得文字理解、分析和生成能力 |
| A1 总智能体 | 接住用户需求，按需调用A2、A3的模块，再统一回复 |

**学校模型不是A1 总智能体。A2、A3不必等A1 总智能体完成，也不需要每次调用模型都经过A1。**

**开发关系：** A1、A2、A3 的程序 → 同一个学校模型 `qwen3.8-27b`。

三个人各自编写处理流程，共用模型调用模块；学校模型不会自动替代总智能体的协调逻辑。

## 2. 三个人分别负责什么

| 人员 | 主责 | 交给其他人什么 |
|---|---|---|
| **A1** | 总调度、多轮协调和结果整合；出行文旅、反诈骗 | 总智能体入口、子任务要求和统一接入规范 |
| **A2** | 健康生活、家庭照护、求助、社区与志愿服务协同 | 能接收任务、查询或处理业务并返回结果的模块 |
| **A3** | 共享记忆机制、非遗文化、老人能力银行 | 记忆公共能力，以及文化和能力银行任务模块 |

- A1决定交给谁、先做什么，不能替A2／A3伪造办理结果。
- A2负责联系服务和跟进状态；A3负责记忆机制和文化成长，各自模块由各自负责人完成。
- 长期记忆由三人共同使用和提交候选，A3主导机制，P2保存和校验权限。

## 3. 学校模型怎么调用

| 配置 | 学校文档提供的值 |
|---|---|
| 方法 | POST |
| 地址 | http://10.138.50.151:8000/v1/chat/completions |
| 模型名 | qwen3.8-27b |
| 请求 | model、messages等，按学校MD文档发送 |
| 回复正文 | choices[0].message.content |
| 访问 | 文档说明校内访问、当前无需API Key；每人需验证自己的网络可达 |

各自程序通过共用的模型客户端调用。语言不强制Python；不需要先登录FinalShell。模型API提供生成能力，业务查询、保存和通知由P2接口执行。

## 4. 总智能体怎么调用A2、A3

按后端v3.0 r1草案，**用户不需要自己选择A2或A3；A1通过P2受控网关委派任务，不直接使用队员的密钥。**

**完整调用顺序：**

1. 老人通过前端表达需求。
2. P2 校验身份并创建任务，交给 A1。
3. A1 理解需求，自行处理或通过 P2 委派 A2、A3。
4. A2、A3 按需查询资料、调用模型和业务工具，将结果交回 P2。
5. P2 保存结果并恢复 A1；A1 整合回复，经 P2 校验后由前端展示。

分工关系：**A1 决定做什么、交给谁；P2 检查是否允许并执行；A2／A3 处理所属业务。**

| 环节 | 各方做什么 | 草案中的入口 |
|---|---|---|
| 用户找总智能体 | 前端发给P2，P2建任务后交给A1 | 前端：POST /api/agent/v3/messages |
| P2调用各Agent | A1、A2、A3各自提供任务接收接口，部署地址由P2配置 | Agent：POST /internal/v3/messages |
| A1委派A2／A3 | A1按动作准备规则登记步骤与动作，再提交目标、任务说明及必要上下文 | P2：POST /internal/agent/v3/delegations |
| 子Agent交结果 | A2／A3按统一格式响应P2，由P2在恢复A1时提供dependencyResults | 使用统一响应，不要求队员另向A1发消息 |
| 需要查资料或执行业务 | 各Agent通过P2受控工具调用 | P2：POST /internal/agent/v3/tools |

**上表均为v3草案路径，不能直接调用当前v2服务。**具体部署地址、字段和确认规则以最终协议为准；学校模型端口不等于这些Agent服务的端口。

## 5. 接入时统一什么格式

大白话：A1发“任务单”，A2／A3交“结果单”。公共格式跟随P2协议，各领域只扩展登记过的业务内容。

| 任务单：P2交给Agent | 结果单：Agent交回P2 |
|---|---|
| 老人、会话、消息和任务标识 | 对应任务、调用ID和基准版本 |
| 本次要做什么 | 已完成、需补充信息、等确认或等依赖 |
| 必要上下文、业务对象及附件引用 | 简短回复与结构化业务结果 |
| 调用凭证与截止时间 | 来源、待核实事项和真实待确认操作ID |

- A1、A2、A3都接同一公共格式，不各造一套返回结构。
- 凭证用于程序访问P2，不放进模型消息。结果不能凭模型文字冒充已通知、已保存或已报名。
- 需要追问或确认时经总入口与P1展示；普通子任务追问和跨任务确认按协议补齐后的规则接入。

## 6. 三个人如何接入协作

**开发与接入顺序：** 对齐任务与结果格式 → 三人分别调用学校模型 → 开发各自模块 → A2／A3 提供任务接口 → P2 登记服务地址和权限 → A1 通过网关调用、整合。

这是协作流程，不要求 A2、A3 等待 A1 全部完成。

| 人员 | 开发动作 |
|---|---|
| A1 | 搭总调度；接已有旅游和反诈骗；按统一格式委派并读取结果 |
| A2 | 写协同模块；能接任务、缺信息时追问、按后端真实状态交结果 |
| A3 | 写记忆与文化模块；提供相关检索和候选处理，不擅自长期保存 |
| P2 | 提供任务与工具网关，登记服务地址和权限，保存状态、确认及业务数据 |
| P1 | 提供统一输入、卡片、追问、确认和状态展示 |

示例：老人说“想学剪纸、别太远、希望有人陪” → A1拆任务 → A3找课程 → 老人选择 → A2处理陪同协助 → P2提供实际状态 → A1统一回复。需要记住兴趣时，再单独走记忆确认。

本文可单独转发，无图片、附件或图表插件依赖。正式字段参考《Agent统一交互协议_v3.0_讨论草案_r1》及后续共同确认版本；模型参数参考学校API文档。


## 7. A1的工作具体到哪些功能

### A1 总智能体：接住整件事

1. 收到需求，判断信息是否足够；不足时先追问一个关键问题。
2. 读取本任务相关的授权资料和记忆。
3. 自行处理旅游、反诈骗，或按需委派 A2、A3。
4. 检查返回内容、依据和未完成事项。
5. 统一回复；需要实际操作时准备具体确认，按后端结果继续跟进。

| 功能 | A1实际开发内容 | 与其他人的交接 |
|---|---|---|
| 理解需求 | 判断新任务、追问回答、修改或取消；识别多个领域 | P2提供会话及候选任务，A1判断业务指向 |
| 任务拆分 | 确定子任务目标、处理顺序、必要性和依赖 | 经P2委派A2／A3，不共享队员密钥 |
| 多轮协调 | 理解“刚才那个”“第二天换一下”；不明确则追问 | 关联任务与业务版本，不随意修改最近对象 |
| 个性化 | 读取本任务相关偏好，当前要求与旧偏好冲突时澄清 | 调用共享记忆能力，不自行维护第二套长期档案 |
| 结果整合 | 保留成功部分，解释失败项，避免相互矛盾 | 从P2接收子任务结构化快照，而非只看工具日志 |
| 确认和恢复 | 说明准备执行的内容；收到决定或依赖完成后继续处理 | P1承载确认，P2执行并回传事实 |
| 公共调用 | 维护模型基础客户端、任务适配与统一回复方式 | A2／A3共用基础代码，各自维护领域逻辑 |

### A1出行文旅：规划、游中服务和调整

| 功能 | 具体内容 | 必要输入或工具 |
|---|---|---|
| 需求收集 | 目的地、日期、同行人、交通、兴趣、休息与步行偏好 | 本次表达及授权档案 |
| 路线与行程 | 景区候选路线、多日草案、交通、吃饭和休息安排 | 地点、路线、交通与开放信息 |
| 适老依据 | 展示台阶、连续步行、座椅和休息点；资料不足则标待核实 | 景区或可核实资料，不能仅靠模型推测 |
| 攻略解析 | 根据授权正文、截图或允许读取的链接提取地点，交用户核对 | 附件和受控链接读取，失败提供正文/截图兜底 |
| 游中问答 | 找厕所、座椅、医务室、出口；景点讲解有资料依据 | 授权位置或手选地点、设施与知识库 |
| 途中调整 | 说累了时找休息点、缩短剩余，保留已游部分 | 后端真实进度；未知则问，不自行推测 |
| 游后小结 | 整理实际游览与反馈，生成可分享内容草案 | P2实际记录；候选偏好交A3，共享另走权限 |

### A1反诈骗：分析，不替老人做资金决定

| 功能 | 具体内容 | 交接边界 |
|---|---|---|
| 内容分析 | 可疑短信、语音转写和截图，提取可疑要求 | 学校模型处理必要内容，附件经P2授权 |
| 风险解释 | 风险程度、具体信号、依据、局限与核实步骤 | 不把模型判断说成官方认定，低风险不等于保证安全 |
| 教育提醒 | 常见案例卡、暂停操作提示、问家属入口 | 平台内明确入口触发，不承诺监控其他App或系统来电 |
| 求助衔接 | 需要家属或人工帮助时形成协同请求 | 交A2，P2检查授权并执行，不自动通知所有家属 |

## 8. A2的工作具体到哪些功能

1. 接收 A1 的协助任务，整理事项及缺失信息。
2. 查询可用资料或服务，形成具体协助方案。
3. 需要确认时由 P1 展示，P2 校验决定并执行。
4. 查询真实处理状态，交回 A1。
5. 将有价值的服务反馈提交为候选记忆。

| 模块 | A2实际开发内容 | 返回给A1什么 |
|---|---|---|
| 健康生活 | 按自愿资料和当天状态给一般饮食、运动、休息建议，必要时转专业人员 | 建议、依据、边界及需要专业协助的事项 |
| 健康提醒 | 整理复诊、作息等提醒内容与时间 | 待确认提醒；实际定时执行由P2提供 |
| 家庭照护 | 陪诊、购物、探视、陪同等需求，整理对象、时间与事项 | 待确认照护任务或缺失问题 |
| 家庭协同 | 多家属分工、留言、主动近况分享、路线建议协同 | 业务对象、授权内状态及后续步骤 |
| 求助与人工 | 整理求助类型、位置来源、必要说明，提交和查询接单处理 | 创建、通知、受理、解决分别报告 |
| 社区活动 | 按兴趣、距离和行动要求筛选普通社区活动，处理报名与提醒 | 活动候选、报名结果和待核实项 |
| 志愿服务 | 陪伴、助行、数字教学等需求与匹配申请，跟进服务、评价与时长 | 匹配/申请/接受/完成状态，不承诺自动有人接单 |
| 记忆反馈 | 整理用户反馈和服务经历，区分一次性与长期信息 | 候选及消息或业务来源，不直接写成永久偏好 |

A2维护公共协同能力，A1和A3需要联系家庭、机构或人工时调用。通知系统、业务数据库和工作人员接单页面不由A2重复实现。

## 9. A3的工作具体到哪些功能

**共同记忆流程：** 各领域提交候选 → A3 检查重复和冲突 → A1/P1 呈现确认 → P2 验证并保存 → 三人按任务和权限使用。

老人纠正、删除或撤回授权后，后续检索和相关上下文必须停止使用失效内容。

| 模块 | A3实际开发内容 | 返回或依赖 |
|---|---|---|
| 候选提取 | 区分临时状态、长期偏好和经历，保留原始来源 | 候选内容、适用领域、敏感程度、来源 |
| 去重与冲突 | 检查是否已有同类偏好，提出新增、合并、替换或保留建议 | 审核建议不能替代老人决定 |
| 相关检索 | 根据任务目的返回少量相关有效记忆 | ID、版本、来源、时间与适用范围；权限由P2检查 |
| 生命周期 | 配合确认、纠正、删除、过期、撤权和缓存失效 | P2提供存储、版本和确认执行能力 |
| 非遗文化 | 非遗、方言和地方文化问答，按兴趣推荐课程 | 有来源的内容与课程候选 |
| 学习记录 | 学习计划、进度、作品和技艺发布；签到/报名工具适配 | P2保存事实，P1展示或上传作品 |
| 能力银行 | 技能、传授意愿、供需匹配与服务流程 | 发布、审核、报名、打卡、佐证、评价、贡献记录 |
| 贡献整理 | 解释确认后的服务和时长记录 | 不由模型自行审核通过、增加时长或创造贡献 |

A3可以依托P2受控入口提供检索算法，不让其他Agent直接读取数据库全部记忆。文化服务需要陪同或人工帮助时调用A2协同能力。

## 10. 公共能力谁维护，谁使用

| 公共能力 | 主责 | 三人共同遵守 |
|---|---|---|
| 模型客户端 | A1牵头 | 共用配置与解析，不同模块保留不同职责提示词 |
| 总体任务编排 | A1 | A2／A3返回统一结果，不自行无限互相委派 |
| 人工与服务协同 | A2 | 其他模块提出协助需求，不各建通知流程 |
| 记忆机制 | A3 | 三人均读取必要记忆、提交候选并处理纠正 |
| 任务与工具网关 | P2 | 按任务权限使用，不将模型分类当作授权 |
| 业务和记忆存储 | P2 | 程序查真实状态，不能以模型回复代替 |
| 用户输入和确认 | P1配合A1 | 统一入口、卡片和按钮，不迫使老人选择内部Agent |

### 两处容易重叠的业务

| 情况 | 明确归属 |
|---|---|
| 文化课程与普通社区活动 | 文化课程由A3负责，普通社区活动由A2负责；共用P2活动和报名基础 |
| 接受志愿帮助与提供个人技能 | 为老人找帮助由A2负责；老人登记技能、提供帮助意愿由A3负责；同一服务复用后端记录 |

## 11. 任务单与结果单怎样真正接起来

### 总智能体交任务时

| 内容 | 谁准备 | 用途 |
|---|---|---|
| 目标与协作领域 | A1程序组织 | 明确只查询、生成建议还是准备业务操作 |
| 老人、会话、父子任务与调用标识 | P2生成和校验 | 保持归属和恢复关系，不由模型编造 |
| 必要业务引用和附件 | A1提出，P2过滤 | 只给完成本任务需要的资料 |
| 截止时间和凭证 | P2提供 | 约束调用时限和工具权限 |

### 子智能体交结果时

| 内容 | 要说明清楚什么 |
|---|---|
| 状态 | 完成、等输入、等确认、等依赖或失败，使用最终约定枚举 |
| 回复 | 简短说明已做什么、尚缺什么，供A1整合 |
| 结构化结果 | 按登记类型返回活动、记忆、协助状态等卡片数据 |
| 来源 | 实际工具、授权附件或登记资料，不编造来源 |
| 待确认操作 | 只引用P2已生成的确认ID，不自行授权 |
| 错误或局限 | 无资料、暂不可用、部分失败、未核实事实分别说明 |

A2／A3不需要另写一个“给A1发消息”的流程：对P2的任务调用返回结果，P2保存后恢复A1。Agent需要调用学校模型时仍可独立使用公共模型客户端。

## 12. 一个完整例子：找课程并找陪同

| 顺序 | 负责人 | 处理内容 |
|---|---|---|
| 1 | 老人、P1、P2 | 老人提出“想学剪纸、别太远、希望有人陪”，P2 建立任务 |
| 2 | A1 | 理解需求，查询必要偏好，经 P2 委派文化查询 |
| 3 | A3 | 返回课程候选、来源和待核实内容，由 P2 交回 A1 |
| 4 | A1、老人 | A1 推荐课程，老人选择；P2 将回答关联到原任务 |
| 5 | A1、A2 | A1 经 P2 委派陪同需求，A2 准备具体协助操作 |
| 6 | P1、老人、P2 | 展示具体内容，老人确认，P2 检查权限并执行、保存 |
| 7 | A2、P2 | 查询实际协助状态，返回结果并恢复 A1 |
| 8 | A1 | 告知老人哪些已完成、哪些仍在等待 |


长期保存“喜欢剪纸”是另一个记忆确认，不因报名或陪同确认而自动生效。没有真实课程、陪同或通知接入时，结果明确标为演示或不可用。

## 13. 每个人最终交什么

| 人员 | 交付内容 |
|---|---|
| A1 | 总调度服务、旅游和反诈骗模块、公共模型客户端、子任务整合与恢复逻辑 |
| A2 | 健康照护、求助和社区志愿模块、协同入口、真实状态解释与恢复逻辑 |
