# 银龄智游平台统一接口协议

版本：v3.0｜日期：2026-10-29｜供 P1、P2、A1、A2、A3 和测试同学使用

这份文档规定平台所有接口统一使用哪个版本、路径和返回格式，也说明 Agent 如何接收任务、调用业务能力和返回结果。先看接口版本规则，再看模板与场景示例。

**v3.0 是本项目唯一的开发目标。现有后端代码可以复用业务逻辑和数据库，但接口路径、Agent任务流程和对外契约都按 v3.0 改造。当前运行服务还没完成这次改造，不要把本文样例发送给现有服务。**

## 版本与实施状态

v3.0 统一 P1 到 P2 的所有公开 API，以及 P2 与 Agent 之间的内部调用。原先各接口不再分别标成“业务 v2”和“Agent v3”。旧文档只作为迁移参考；后续开发、测试和联调都以 v3.0 文档为准。

| 内容 | 当前状态 |
|---|---|
| 统一版本 | 所有 P1→P2 公开接口使用 `/api/v3/...`；P2→Agent 使用 `/internal/v3/...`；Agent→P2受控能力使用 `/internal/agent/v3/...` |
| 统一返回 | 所有HTTP接口成功或失败都使用 `{code,message,data}`；HTTP状态表达传输/权限/参数结果，`code`表达业务结果 |
| 业务请求正文 | 按业务填写各自字段，例如档案字段、求助位置、反馈内容；不强行包进 Agent 的 `input/context` |
| Agent请求正文 | 按本文的 MessageRequest、InvocationRequest、AgentResponse 等 v3结构 |
| 首批范围 | 28项现有业务操作迁到v3路径，加上任务接收查询、A1委派、子问题与恢复、受控确认、共享记忆基础流程 |
| 延后范围 | 自动任务转交、SSE、真实报名、复杂多日行程、支付和真实外部通知 |

现有业务接口的详细字段见 [P2后端接口文档 v3.0](P2后端接口文档_v3.0.md) 和 [字段附录 v3.0](P2接口字段附录_v3.0.md)。配套 JSON Schema、Agent报文样例和本地校验方法见 [v3.0 联调包说明](agent-v3-r3/README.md)。格式校验通过不代表任务恢复、权限、幂等和外部副作用已经通过服务测试。

## 所有接口如何统一到 v3.0

### 1. 路径按一套版本迁移

P1调用P2的业务接口统一加`/api/v3`前缀；P1不需要判断某个功能原来属于哪个版本。Agent新增的任务接口也放在同一前缀下。P2与Agent的内部入口统一使用v3路径。

| 原有能力 | v3.0路径示例 |
|---|---|
| 档案 | `PATCH /api/v3/profile`、`GET /api/v3/profile` |
| 景点和路线 | `GET /api/v3/spots`、`GET /api/v3/routes`、`GET /api/v3/routes/{id}/map` |
| 家属授权 | `/api/v3/family-relations...`、`GET /api/v3/family/elder`、`GET /api/v3/notifications` |
| 游览和求助 | `/api/v3/trips...`、`/api/v3/help-events...`、`/api/v3/travel-records...` |
| 语音 | `/api/v3/speech/transcriptions`、`/api/v3/speech/syntheses` |
| Agent消息和任务 | `/api/v3/agent/messages`、`/api/v3/agent/tasks/{id}`、`/api/v3/agent/confirmations...` |
| P2调用Agent | `/internal/v3/messages`、`/internal/v3/invocations/{id}` |
| Agent调用P2工具 | `/internal/agent/v3/tools`、`/internal/agent/v3/delegations`、`/internal/agent/v3/actions` |

28项已实现业务操作的完整路径清单和字段见P2 v3接口文档。任务、确认、附件、记忆等新增操作以本协议及联调Schema为准。

### 2. 业务字段仍按业务填写

“所有接口统一成v3.0”表示接口版本、路径规则和返回外层统一，不是把所有请求改成一个长得一样的JSON。例如建档仍提交档案字段，创建求助仍提交求助字段，Agent发消息才使用`input`和`context`。这样既只有一套版本，也能按每种业务校验必填项和权限。

### 3. 改造现有后端时保留可复用的部分

P2可以继续使用现有数据表、业务服务和外部服务适配。需要统一改造的是对外路由、DTO/校验、响应和错误格式、权限与幂等边界、Agent受控工具注册以及OpenAPI/测试集合。旧路径不作为新开发入口；联调通过后不长期维护v2与v3两套路由。

## 整体流程

用户仍然只对一个入口说话。P2接收请求并建立任务，A1负责理解需求、安排协作和组织回复；涉及查询或实际操作，统一经过P2校验。

```text
用户 → P1页面 → P2接收消息、建任务 → A1总智能体
                                      ├─ 自己处理文旅、反诈骗
                                      ├─ 经P2调用A2处理相关领域
                                      └─ 经P2调用A3处理相关领域

A1/A2/A3需要查资料、用记忆或办事情 → 调P2工具
P2校验身份、任务范围、确认凭证 → 执行并保存真实结果
A1整合回复 → P2校验并保存 → P1展示文字、业务卡片和确认按钮
```

**A1决定需要谁协作；P2判断这次调用是否允许，并执行已约定的业务动作。P2不再根据一个intent自行挑选领域Agent。**

## 一、职责与实现状态

### 1. 谁负责什么

| 负责人 | 主要工作 | 不负责代替谁做什么 |
|---|---|---|
| A1 | 总智能体；理解需求、拆任务、多轮协调、调用协作者、整合结果；文旅、反诈骗 | 不绕过P2直接保存、授权、通知或写长期记忆 |
| A2 | 健康生活、家庭照护、求助、社区和志愿服务协同 | 不凭模型判断修改授权或生成“已送达”的事实 |
| A3 | 主导共享长期记忆机制；非遗文化、能力银行 | 不把记忆当成业务数据库或用户授权 |
| P2 | 身份权限、受控网关、业务执行、会话任务记录、确认凭证、存储和状态 | 不再写一套与A1并行的业务任务编排逻辑 |
| P1 | 对话、卡片、进度、确认/拒绝/取消及恢复交互 | 不根据回复文字推断业务已经完成 |

A1/A2/A3共同使用共享记忆。A3主导提取、检索、去重和冲突处理方法，P2负责最终访问控制、状态和存储。需要向量库或独立检索服务时，由A3与P2另定部署和数据删除接口。

### 2. 哪些有了，哪些没有

| 内容 | 状态 | 说明 |
|---|---|---|
| v2.0的input/reply、统一响应外层 | 已实现 | 当前代码采用v2.0 |
| 老人归属检查、独立Agent密钥、追踪、工具白名单与执行记录 | 已实现 | 现有机制只支持当前调用范围，不能直接当成持久任务网关 |
| 格式/文本有效性检查、部分上游错误处理 | 已实现 | 不等于事实核查或完整内容审核 |
| 求助及游后反馈的动作幂等 | 已实现 | 不是所有业务都已支持幂等 |
| 高德地图、档案、家属授权、游览、求助、反馈等业务能力 | 已实现 | 新开发统一按[P2接口文档v3.0](P2后端接口文档_v3.0.md)及字段附录调用 |
| 真实A1/A2/A3替换mock | 待联调 | 各负责人按当前协议提供服务后才能接入 |
| A1总调度和跨领域子任务 | 未实现 | v3.0定义了接口和运行规则 |
| 持久会话、任务查询取消、用户确认、结构化结果注册表 | 未实现 | 需要按本文实现并联调 |
| 共享长期记忆、图片附件、SSE和新领域写入工具 | 分批实现 | 本协议不表示这些能力已全部开放 |

本文“待联调”仅指已有适配基础但还没接上真实服务；不把尚未开发的功能标成待联调。

## 二、四个标准模板

下面ID为便于阅读的示例编号。正式ID由P2生成、作为不透明字符串使用，调用方不要根据前缀判断权限。时间统一ISO 8601 UTC。示例不是真实业务记录。

### 模板A：前端向P2发送消息

消息提交接口：`POST /api/v3/agent/messages`。

```http
Content-Type: application/json
Idempotency-Key: msg-action-20261029-001
```

```json
{
  "protocolVersion": "3.0",
  "userId": "u100",
  "conversationId": null,
  "continueTaskId": null,
  "input": {
    "text": "明天安排一个轻松的文化活动",
    "attachmentIds": [],
    "responseTo": null
  },
  "context": {
    "businessRefs": []
  },
  "relatedTaskId": null
}
```

| 字段 | 含义 | 规则 |
|---|---|---|
| protocolVersion | 格式版本 | 固定字符串 `3.0` |
| userId | 服务对象老人 | 目前只允许老人本人发起；家属代办以后单独授权 |
| conversationId | 同一段对话 | 首条传null，P2创建并返回；后续原样带回 |
| continueTaskId | 是否继续已有任务 | 新任务传null；继续必须是本人、本会话、未结束任务，由P2检查状态 |
| relatedTaskId | 新任务参考了哪项旧任务 | 修改终态任务时填原taskId；只建立关联，不恢复或继承旧授权 |
| input.text | 用户这次说的话 | 最多2000字符；文本和附件至少有一项 |
| input.attachmentIds | 已上传的附件 | 不传本地路径或任意图片URL；首批最多4个图片附件 |
| context.businessRefs | 明确指向的业务对象 | 每项包含type、id、version；没有就[] |

intent不作为必填参数。分类由A1产生，可记录主意图和多个domains，但不能据此限制只能调用一个领域。domains首批沿用tourism、fraud、health、care、help、community、volunteer、culture、ability；memory属于共享能力，不强制增加memory领域。分类不是授权，工具是否允许仍由P2判断。

### 模板B：P2先返回“已经接收”，不是假装处理完了

HTTP继续使用200，外层仍为code/message/data。这里code=OK只表示消息已接收、任务已创建或已关联。

```json
{
  "code": "OK",
  "message": "消息已接收",
  "data": {
    "conversationId": "conv-001",
    "messageId": "msg-001",
    "taskId": "task-001",
    "taskVersion": 1,
    "taskStatus": "QUEUED",
    "reply": null,
    "results": [],
    "confirmationIds": []
  }
}
```

P1先保留这些ID，再查询任务或订阅事件，不要把message里的“消息已接收”当成最终Agent回复。

发送消息的Idempotency-Key在v3设为必填：同一老人、同一Key和相同规范化请求，24小时内返回同一messageId/taskId，不重复建任务；同Key换正文或会话返回409。它只负责收消息去重，不能替代后续每个业务动作的幂等Key。

### 模板C：P2把任务交给A1

拟由各Agent提供：`POST /internal/v3/messages`。P2在后台工作线程发起，不占用前端HTTP连接一直等待。

```http
X-Agent-Key: <A1自己的服务密钥>
X-Trace-Id: <本次调用的追踪ID>
Content-Type: application/json
```

```json
{
  "protocolVersion": "3.0",
  "userId": "u100",
  "conversationId": "conv-001",
  "messageId": "msg-001",
  "task": {
    "id": "task-001",
    "parentTaskId": null,
    "version": 2,
    "attempt": 1,
    "invocationId": "invoke-001",
    "deadlineAt": "2026-10-29T02:01:00Z"
  },
  "input": {
    "text": "明天安排一个轻松的文化活动",
    "attachmentIds": []
  },
  "context": {
    "businessRefs": [],
    "history": [],
    "completedEffects": [],
    "reason": "USER_MESSAGE",
    "candidateTasks": [],
    "dependencyResults": [],
    "confirmationResults": [],
    "actionLedger": [],
    "planSteps": [],
    "readSet": {
      "memoryRevision": 0,
      "authorizationRevision": 0,
      "provenanceRefs": []
    },
    "inputResponse": null,
    "pendingInputRequests": []
  },
  "capabilityToken": "<P2签发的本次调用凭证>"
}
```

history是经权限筛选的历史消息片段，每项至少有messageId、role、text、createdAt、attachmentIds；role只允许user/assistant。任务恢复时completedEffects携带已经确认的effectId、业务对象和执行状态，避免Agent重新执行。reason取USER_MESSAGE、INPUT_PROVIDED、CHILDREN_FINISHED、CHILD_INPUT_REQUIRED、CHILD_CONFIRMATION_REQUIRED、CONFIRMATION_DECIDED、RECOVERY之一。dependencyResults交付子任务结果，actionLedger交付所有动作状态，具体结构见第五、六节；completedEffects只是已成功效果的便捷摘要，不能代替完整账本。

本轮deadlineAt是本次调用截止时间，不是整个根任务的24小时有效期。Agent回传的messageId指本轮来源用户消息，P2保存正式助手回复时另生成assistantMessageId。

A1只取得完成当前任务所需的资料，不默认收到全部健康资料、家属信息和长期记忆。附件列表也不等于已经允许把所有文件传给任意模型服务。

### 模板D：A1返回本次处理结果

```json
{
  "code": "OK",
  "message": "本次处理完成",
  "data": {
    "conversationId": "conv-001",
    "messageId": "msg-001",
    "taskId": "task-001",
    "baseTaskVersion": 2,
    "invocationId": "invoke-001",
    "intent": "tourism",
    "domains": [
      "tourism",
      "culture"
    ],
    "control": {
      "next": "COMPLETE",
      "outcome": "SUCCEEDED",
      "dependencyTaskIds": [],
      "inputRequest": null
    },
    "reply": {
      "text": "我整理好了可供选择的演示活动，请先核实开放时间。",
      "speechRate": 0.8,
      "audioUrl": null
    },
    "results": [],
    "confirmationIds": [],
    "tools": [],
    "handoff": null,
    "usedMemoryRefs": []
  }
}
```

| 字段 | 怎么使用 |
|---|---|
| baseTaskVersion / invocationId | 回传本轮交付时的版本和调用ID；P2按有效调用记录验收，旧调用结果不能覆盖新状态 |
| intent / domains | 主分类和涉及领域，属于说明信息，不是权限凭证 |
| control | 建议下一步，P2检查依赖、确认和实际执行结果后才改变任务状态 |
| reply | 给用户的回复；speechRate仍为0.5～1.5，audioUrl当前仍null |
| results | 有类型的业务卡片，结构见第七节 |
| confirmationIds | P2已生成的待确认操作，不接受Agent自己编造的ID |
| tools | Agent推荐返回[]，P2补充真实工具记录；非空则必须与真实记录一致 |
| handoff | 沿用v2转人工建议结构，不代表真实通知或转接成功 |

control.next允许COMPLETE、WAIT_CONFIRMATION、WAIT_DEPENDENCIES、WAIT_INPUT。COMPLETE时outcome只能为SUCCEEDED、PARTIALLY_SUCCEEDED或FAILED；其他next时outcome为null。WAIT_INPUT必须给出inputRequest；WAIT_CONFIRMATION必须关联有效待确认操作；WAIT_DEPENDENCIES只能引用本任务经P2创建的子任务，可以是仍在运行的子任务，也可以是刚刚完成但结果尚未交付给本父任务的子任务。P2不能只信模型的一句“已完成”。

一次调用期间的合法进度更新可能增加taskVersion，但不自动让本轮结果失效。P2核对baseTaskVersion是否等于本轮交付记录中的版本，并检查invocationId仍为有效调用；新用户修改、取消、超时或权限变化会使旧调用失效。带有效input.responseTo的消息是对已登记问题的补充，P2按INPUT_PROVIDED处理，不按“修改整个任务目标”处理：只恢复ownerTaskId对应的等待任务，不自动取消独立子任务或无关确认。若答案实际改变了其他动作的参数、范围或权限，P2只使受影响的调用/确认失效，并重新校验；无关分支继续有效。只有当前有效调用的结果可落地，避免进度更新和最终回复互相冲突。

## 三、会话、消息、任务和业务版本怎么区分

| 标识 | 谁生成 | 用途 |
|---|---|---|
| conversationId | P2 | 把同一段对话串起来，归属一位老人 |
| messageId | P2 | 一条用户消息或一条可展示的助手回复，各自有独立ID |
| taskId | P2 | 一项需要持续处理的任务，一段对话可有多个任务 |
| parentTaskId | P2 | 子任务指向父任务，根任务为null |
| taskVersion | P2 | 快照修改时递增；不能把普通进度递增误判为本轮调用失效 |
| 业务对象id/version | 对应P2业务模块 | 指明修改哪份行程、报名或记录以及基于哪一版 |
| X-Trace-Id | P2追踪机制 | 查一次调用的日志；不是会话、任务、幂等或授权ID |

例如“第二天改一下”：A1结合history理解指代，再明确itineraryId和version；不明确时追问，不能随便改最近一份行程。原有Trip是一次游览，不自动等于新的多日行程对象。

同一运行中任务收到新消息时，P2串行处理：先标记旧调用不可再产生新动作，核查已在执行的动作，再交付新一轮输入。A1不能在两个并发调用里同时修改同一个任务。等待确认时修改需求，应使旧确认INVALIDATED并重新准备，不能沿用旧参数让用户确认。

任务查询接口：

- `GET /api/v3/agent/conversations/{id}/messages?limit=20&cursor=...`：本人分页读历史。
- `GET /api/v3/agent/tasks/{id}`：本人查任务完整快照。
- `POST /api/v3/agent/tasks/{id}/cancel`：本人明确取消，正文带expectedVersion和reason。

任务查询data固定包含taskId、conversationId、sourceMessageId、parentTaskId、relatedTaskId、version、status、phase、reply、results、inputRequest、confirmationIds、childTasks、pendingInputRequests、effects、error、createdAt、updatedAt、expiresAt。reply是最新通过校验的回复，没有时null；error是脱敏错误对象，没有时null。

childTasks每项含taskId、targetAgent、status、required。effects每项含effectId、actionId、tool、businessRef、executionStatus、externalStatus、createdAt。P1展示状态应读这些字段，不从reply.text猜测。

开发联调期可先按历史原文7天、任务执行记录30天、脱敏安全日志30天配置；上线前由数据负责人核定保留期限。删除会话不自动删除求助、报名等独立业务记录，但要停止把已删消息用于后续模型上下文。长期记忆也有独立查看和删除入口，不能以删除对话代替删除记忆。

### 普通追问怎么返回

例如A1还不知道目的城市，可以返回以下control，reply.text同步写“你准备去哪座城市？”。这是Agent向P2提交的问题内容，不是确认保存，也不能把任务标记完成。Agent必须省略`version`，也不能传`null`或自行填`1`。

```json
{
  "next": "WAIT_INPUT",
  "outcome": null,
  "dependencyTaskIds": [],
  "inputRequest": {
    "inputRequestId": "9f75ab8a-73d4-4e26-909f-2f2e67b95d42",
    "question": "你准备去哪座城市？",
    "requiredFields": [
      "destinationCity"
    ],
    "options": [],
    "allowFreeText": true
  }
}
```

Agent提交的新inputRequest只含inputRequestId、question、requiredFields、options、allowFreeText。每个Agent程序为一个新问题生成UUID v4作为inputRequestId，并在本次调用重试/重放时保持不变；不同问题不得复用。P2对inputRequestId建立全局唯一约束，同ID、同归属、同规范化问题内容的重放按幂等处理；ID已属于其他任务/调用，或同ID对应不同问题内容时，返回409/INPUT_REQUEST_ID_CONFLICT，不覆盖旧问题。P2登记成功后补上ownerTaskId及从1开始递增的version，并在后续任务快照、进度事件、任务查询和pendingInputRequests中返回登记版问题；初始消息受理响应只返回受理信息，不要求同步包含问题。问题实质修订保留同一问题ID、递增version；另一个问题必须新建ID。requiredFields是补充资料的键，不允许伪装成权限或执行指令。options每项为id、label、value，先支持纯文本选项。

P2置问题所属任务为WAITING_INPUT，释放模型执行位，不计处理预算；最多等到任务绝对expiresAt（建议创建后24小时）。P1发送补充消息时带conversationId、continueTaskId，并在input.responseTo中带ownerTaskId、inputRequestId、P2返回的version和可选selectedOptionId，input.text仍保留用户原话。P2检查问题属于该任务、尚未失效，再以INPUT_PROVIDED恢复ownerTaskId，context.inputResponse带问题及用户回答。不会把追问答案自动当成APPROVE或新任务目标。

### 没有continueTaskId，不由P2猜“最近那个”

P2按本人、本会话筛选最多5个未结束候选任务，在context.candidateTasks提供taskId、summary、status、updatedAt、inputRequestId和businessRefs；summary只包含该用户当前可见的脱敏任务摘要。顺序可以按更新时间，但不能仅据此选定任务。

首批不支持自动转交，不接受ROUTE_INPUT/REDIRECTED。A1判断为新需求就继续新任务；像“刚才那个”但缺continueTaskId时，A1返回WAIT_INPUT并提示候选任务，P1让用户明确选择，下一条消息携带选择的continueTaskId。

新的“选择任务”提示任务只有控制用途，不产生业务动作。P1必须取消/关闭该提示任务（调用普通取消入口，保留其记录），再把用户回答提交给目标任务；可在新消息relatedTaskId记录提示任务以追踪。两步失败时分别查询，不自动合并任务，也不重放业务。P2不能盲选最近任务。已经结束的目标用新任务+relatedTaskId处理，不能恢复终态。自动转交留待后续版本评估，不属于首批范围。

## 四、任务状态和恢复

| status | 页面含义 | 说明 |
|---|---|---|
| QUEUED | 排队中 | P2已保存，尚未开始 |
| RUNNING | 处理中 | 正在执行本轮模型或工具调用 |
| WAITING_DEPENDENCIES | 等协作结果 | 存在未结束子任务 |
| WAITING_INPUT | 等你补充信息 | 普通追问，不是操作确认，不占模型并发 |
| WAITING_CONFIRMATION | 等你确认 | 不执行需要确认的动作 |
| SUCCEEDED | 已完成 | 所需处理已结束，不等于所有外部服务已送达 |
| PARTIALLY_SUCCEEDED | 部分完成 | 至少一部分有结果，但有明确失败或未完成项 |
| FAILED | 失败 | 未达到任务目标，已成功的业务操作仍保留 |
| CANCEL_REQUESTED | 正在取消 | 已停止安排新动作，等待正在执行的动作核查 |
| CANCELLED | 已取消 | 后续执行停止，不代表已执行操作撤销 |
| EXPIRED | 已过期 | 不再接受继续执行或确认 |

正常流转：QUEUED → RUNNING → 等输入/等依赖/等确认 → RUNNING → 结束。SUCCEEDED、PARTIALLY_SUCCEEDED、FAILED、CANCELLED、EXPIRED为终态，不直接改回处理中；重新办理创建新任务，并带关联记录供核查。

P2保存每次实际工具结果和可恢复检查点。子任务结束或用户完成确认后，P2按同一taskId重新调用A1，签发新调用凭证，并提供已完成的effects。A1决定剩余业务步骤；P2只负责恢复触发、权限和执行控制。不能因为工作线程重启就把整个任务从头无条件重做。

页面关闭或网络断开不取消任务。重新打开后用taskId查询。用户取消时：吊销后续调用权限、请求取消未开始子任务、拒绝新写操作；已发出的外部请求先标记结果未知并核查。确需退款、撤销报名、撤回分享，应走各业务自己的补偿动作，不能假装数据库回滚能撤回外部操作。

## 五、A1怎样调用其他Agent

P2受控委派入口：`POST /internal/agent/v3/delegations`。

```json
{
  "protocolVersion": "3.0",
  "conversationId": "conv-001",
  "taskId": "task-001",
  "actionId": "action-find-culture-001",
  "input": {
    "targetAgent": "a3",
    "domain": "culture",
    "required": true,
    "instruction": "查找明天适合短时参与的文化活动，不报名、不通知",
    "attachmentIds": [],
    "businessRefs": []
  }
}
```

通过X-Agent-Key识别A1，通过X-Agent-Context携带A1当前capabilityToken。P2根据父任务核实userId，不允许靠正文切换老人。actionId由下面的动作准备入口分配并记录；委派时也要为agent.delegate准备动作，参数包含目标Agent和子任务说明。同一子任务的重试沿用同一actionId。A1不自行使用A3密钥。

成功data返回childTaskId、parentTaskId、targetAgent、status。P2用A3自己的服务通道和独立子任务凭证调用A3，父Agent的凭证不传给子Agent。

父任务等待子任务时释放模型执行并发，不能让A1占着全部执行位同步轮询，导致子任务永远排不上。

A2/A3的消息格式与模板C一致，input.text换成子任务说明，task.parentTaskId指向父任务。子任务响应使用模板D相同外层；reply供A1理解，results提供可整合的结构化内容。

**首批只允许A1调用A2/A3，子Agent不再继续委派。** 最大父子深度1层，每个根任务最多6个子任务，同时运行最多2个。另限制每个根任务最多40次工具尝试、每个子任务最多10次；所有额度以P2记录为准。以后确需更深编排，再单独修改规则，不能允许任意互相调用形成环。

一个子任务失败，不能把另一个成功结果丢掉。A1根据required与任务目标整合，P2保存每个子任务状态。能交付部分结果时PARTIALLY_SUCCEEDED，并在卡片中列出失败项；没有可靠替代资料时不能由模型编造。

### 子任务结果如何交回A1

恢复时context.dependencyResults必须交付本轮依赖子任务的实际快照，而不只是tools或completedEffects。示例：

```json
{
  "dependencyResults": [
    {
      "taskId": "task-child-001",
      "parentTaskId": "task-001",
      "targetAgent": "a3",
      "domain": "culture",
      "required": true,
      "version": 5,
      "status": "SUCCEEDED",
      "reply": {
        "text": "已查到一项演示文化活动。",
        "speechRate": 0.8,
        "audioUrl": null
      },
      "results": [],
      "confirmationIds": [],
      "effectIds": [],
      "error": null,
      "completedAt": "2026-10-29T02:00:20Z",
      "inputRequest": null
    }
  ]
}
```

results在真实调用中填写该子任务已验证的卡片完整对象，不是只给resultId；空数组表示本例省略具体卡片内容。错误结构为code、message、retryable，必须脱敏。P2过滤不允许传给父Agent的敏感内容，父任务不能借查看子结果扩大数据权限。

首批采用屏障规则：同一轮dependencyTaskIds全部进入终态后，只恢复父任务一次。可选子任务失败也等本轮其他依赖结束，再交A1统一整合；不做每到一条就并发恢复。A1此时可给出部分结果、失败说明或准备新的有限子任务，但仍受根任务预算和次数限制。

required=true的失败必须作为未满足依赖交给A1，禁止无说明标全成功。A1如果找到合规替代，需要明确记录替代结果；否则PARTIALLY_SUCCEEDED或FAILED。required=false失败不自动让整体失败，但不能隐藏该项失败。

P2保存resumeGeneration和本轮依赖集合摘要，通过唯一恢复记录加任务锁保证只入队一次；父任务同一时刻只允许一个有效invocationId。若依赖运行期间父任务收到用户修改或取消，先失效旧恢复代次，再按新任务决策，迟到子结果只归档不自动写回新任务。

### 子任务可能先于父任务进入等待状态完成

子任务完成事件可能先到，A1稍后才返回WAIT_DEPENDENCIES。P2不能因子任务已是终态而拒绝依赖，也不能只等一个已经发过的完成事件。处理父响应时，P2在同一受控事务中登记依赖集合、刷新每个子任务的当前状态并决定父任务状态：

1. 依赖全部已进入可交付终态：不进入实际等待，立即将父任务排入一次CHILDREN_FINISHED恢复，并携带已保存的dependencyResults。
2. 仍有依赖未结束：先保存WAITING_DEPENDENCIES，再由后续子任务状态事件触发同一恢复检查。
3. 注册依赖与最后一个子任务完成并发：无论由登记事务还是完成事务先观察到“全部终态”，都用相同的resumeGeneration和唯一恢复记录争抢调度；只允许一方入队，另一方读到已调度结果后结束。

父任务恢复调用必须在调度前再次读取最新子任务快照。已完成子任务保留原结果和版本；不得要求子Agent重复运行。子任务等待老人补充信息时仍不是终态，按“子问题经A1提前提示”流程继续，不伪装成已完成。

### 子任务需要确认，提前提示但不抢执行权

子任务可以返回WAIT_CONFIRMATION；confirmation.ownerTaskId必须是该子任务。P2在本轮未结束前，可按新的确认或确认版本触发CHILD_CONFIRMATION_REQUIRED恢复父A1，用于解释和汇总待确认操作；子任务追问也允许提前提示（见下），均不代表子任务完成。

父任务可呈现后代的confirmationIds并进入WAITING_CONFIRMATION，但不能改ownerTaskId、参数或替代确认。每个新的有效确认或确认版本按confirmationId+version去重。多个事件短时间到达可合并一次提示，P2在一次恢复中给出当前全部有效待确认项。父任务正在处理时，新的提示记入待处理集合，当前调用结束再串行交付；不能漏掉稍后由A2/A3产生的其他确认。已决定、过期或失效的旧确认不能重新弹出；每个操作仍分别授权，不能合并成一个总同意按钮。

用户决定后，P2执行对应子任务绑定动作，先恢复ownerTaskId对应的A2/A3。子任务形成最终结果后，再按依赖屏障恢复A1。拒绝不会凭空生成“执行失败”：子Agent说明哪些目标无法继续，并返回相应结果；其他独立确认可以继续。根任务取消会使未决定的后代确认失效。

### 子任务普通追问也必须提前交给A1

A2/A3返回control.next=WAIT_INPUT时，P2先登记inputRequest，绑定ownerTaskId、rootTaskId、inputRequestId、version。普通依赖屏障暂时让出一个提示机会，通过CHILD_INPUT_REQUIRED把问题交A1；不等这个子任务结束才提问，否则会互相等待。

A1统一解释问题。可以把多个问题放在同一段回复或页面列表中，但每个问题保留原ownerTaskId/inputRequestId/version，不能改变选项含义、字段或把答复变成操作同意。A1转呈子问题时，`inputRequestId`必须逐字原样保留；`question`、`requiredFields`、`options`、`allowFreeText`也必须与P2登记版一致。P2把这个ID识别为对现有问题的引用，不为A1另建问题、不更换ownerTaskId或version；只允许引用当前任务树内已登记且仍有效的问题。A1自己的新问题才由A1程序生成新UUID。父A1不能凭输出伪造子问题。任务查询中的pendingInputRequests提供当前全部有效问题，P1可逐项展示。已知ID但不属于当前老人/任务树，或问题已经回答、过期、失效，均拒绝，不返回其他任务信息。

P1提交答案时continueTaskId填根任务，input.responseTo携带原ownerTaskId、inputRequestId、version及可选selectedOptionId，input.text保留用户原话。P2核对老人、会话、根任务、子任务归属、问题版本及WAITING_INPUT状态，先以INPUT_PROVIDED把答案交回原A2/A3；没有明确绑定的自由文本先由A1澄清，不猜测要回答哪个子问题。

一个消息首批只回答一个问题。多问题分别提交，不把一句含糊的“都可以”分发给所有子任务。重复消息沿用消息Key，不重复恢复；不同消息重复回答已结束/失效问题返回409/QUESTION_NOT_PENDING，要求刷新。子任务重新提问时问题版本递增，旧答案不得覆盖。

子任务得到答案后继续运行；完成后再按依赖屏障恢复A1整合。根任务等待问题不占模型执行位，其他独立子任务可以继续。根任务取消、过期或用户改了任务目标时，对应未回答子问题一起失效。多个子问题的通知按问题ID+version去重、可合并且串行交付，规则与多项确认提示一致。

## 六、工具调用、确认和幂等

### 1. 工具调用模板

P2受控工具入口：`POST /internal/agent/v3/tools`。

```json
{
  "protocolVersion": "3.0",
  "taskId": "task-001",
  "actionId": "action-route-001",
  "input": {
    "tool": "route.recommend",
    "args": {
      "walkDurationMin": 60,
      "avoidSteps": true
    },
    "confirmationId": null
  },
  "stepId": "step-route-001"
}
```

请求头为调用方自己的X-Agent-Key，以及X-Agent-Context临时凭证。userId由任务归属确定，不从args信任。actionId是P2记录的一次具体动作，必须先准备，再执行。

准备入口拟为`POST /internal/agent/v3/actions`，也称action.prepare能力。它本身不需要actionId，避免先有动作ID才能申请动作ID。正文为protocolVersion、taskId、input；input包含tool及完整args，并带P2已保存的stepId；请求头Idempotency-Key使用该步骤登记的prepareKey。P2校验工具和参数、保存规范化全文及摘要，返回actionId、是否需确认、当前状态。这个入口不执行目标工具。工具注册表还要指定唯一执行入口：普通业务走tools，agent.delegate走delegations，确认准备走confirmations；不能同一actionId从两个入口各执行一次。

后续执行只允许使用已准备的相同tool和args；参数改变要重新准备。读取动作也有actionId以关联调用记录，不要求用户逐一确认。准备/委派请求同Key异参数409；同Key同参数返回同一个动作，去重记录建议保留7天。

响应仍为code/message/data。成功data包含actionId、effectId（纯读可为null）、tool、executionStatus、businessRef、result、replayed。result是对应工具的业务对象。失败返回data=null，但已存在actionId仍可通过任务effects或动作查询核查，不能因响应丢失认为没执行。

executionStatus允许NOT_STARTED、RUNNING、SUCCEEDED、FAILED、UNKNOWN。外部结果放externalStatus，例如通知QUEUED/SENT/DELIVERED/FAILED，不把SUCCEEDED直接解释为外部通知送达。

拟提供内部`GET /internal/agent/v3/actions/{id}`，只允许当前Agent访问被授权任务中的动作。P2只返回实际记录，模型不能上报一个伪造effect来改变账本。

### 2. 哪些动作需要确认

| 操作 | v3.0规则 |
|---|---|
| 查询公共资料、生成未保存的候选方案 | 不要求确认；仍检查权限 |
| 内部暂存、反复修改未生效行程草案 | 不逐次要求业务确认；仅在当前授权范围临时存储，不生成正式行程、报名或共享 |
| 正式保存行程、让行程修改生效、活动报名、提交服务申请 | 要确认具体内容 |
| 新增或扩大信息共享范围 | 要确认对象、字段、目的和有效期 |
| 新增长期记忆、改变长期记忆或扩大使用领域 | 要确认；不能用一次同意永久接受所有后续推断 |
| 删除记忆 | 本人明确操作，可通过同一确认入口完成 |
| 直接求助按钮 | 保留现有直接创建方式，不为救急增加重复对话确认 |
| Agent推断的求助、通知家属或外部协同 | 默认先确认；紧急例外及通知范围由A2、P2、P1另行明确，未确认前不放开 |

共享授权以实际授权表为准。任何工具扩展都不能把“已同意保存行程”同时解释为“已同意共享位置”。

### 3. 确认不是一个confirmed字段

Agent先准备动作，再通过`POST /internal/agent/v3/confirmations`准备确认，正文包含protocolVersion、taskId、actionId。这一入口称confirmation.prepare能力，不需要提前存在confirmationId，也不执行原业务。P2保存完整操作参数及规范化摘要、老人、任务、tool、业务对象版本和权限要求，生成confirmationId。Agent不能修改保存后的操作内容，只能重新准备新的操作。

P1从P2查询待确认内容，再显示同意/拒绝按钮。确认接口：

- `GET /api/v3/agent/confirmations/{id}`：查P2保存的完整操作内容。
- `POST /api/v3/agent/confirmations/{id}/decision`：本人作决定。

```json
{
  "protocolVersion": "3.0",
  "decision": "APPROVE",
  "expectedVersion": 1
}
```

决定接口必须携带Idempotency-Key。decision支持APPROVE、REJECT、CANCEL。确认对象状态为PENDING、APPROVED、EXECUTING、EXECUTED、EXECUTION_FAILED、EXECUTION_UNKNOWN、REJECTED、CANCELLED、EXPIRED、INVALIDATED。确认对象另外返回ownerTaskId、rootTaskId、actionId、actionStatus、lastError、canRetry、version。

APPROVE后P2重新核查权限、任务状态、参数摘要及业务版本，再由服务端执行绑定动作，不等待模型再次“确认”。执行与效果写入应在可事务化范围内原子提交；外部副作用经持久执行记录和必要的outbox处理。重复同一决定不重复执行；已拒绝后再同意、业务版本变更、过期或参数被改均409并要求重新准备。

默认有效期建议10分钟，允许用户查看后重新准备。不能把等待确认算成模型一直在线运行。用户用文字说“同意”时，A1可定位候选确认，但不能自行提交APPROVE；首批仍通过P1明确按钮。后续要支持语音确认，必须绑定刚播报的具体操作并另行验收。

### 确认失败或结果未知，页面显示什么

- EXECUTED：绑定动作确实成功，但通知投递、工作人员受理等外部阶段仍看各业务状态。
- EXECUTION_FAILED：P2已经得到明确失败，返回lastError和actionStatus=FAILED。canRetry只作为服务端判断，前端不能直接重新发一次同意来重复执行。
- EXECUTION_UNKNOWN：请求已发出但暂不能确认结果，actionStatus=UNKNOWN。P1显示“正在核查，先不要重复操作”，P2按业务查询或外部幂等凭证核查。

查询仍使用GET confirmations/{id}及GET tasks/{id}。确认决定幂等重放只返回既有决定和最新可查询位置，不重新触发执行。明确失败且允许重试时，由P2登记新的执行attempt，沿用同一业务actionId/外部幂等键；UNKNOWN核查前不得重试。参数改变、授权变化或需新的用户决定时，必须新建确认，旧确认不得复活。

一项确认只绑定一项具体业务动作。多步办理需要逐项明确；一个总确认不能作为对任意后续动作的授权。跨任务的确认按第五节ownerTaskId逐级恢复，父A1只负责解释与整合。

### 4. 业务版本和幂等

修改必须带businessRef.version作为期望版本。P2在执行时比较，过时返回409/STALE_VERSION，不覆盖已更新对象。既有未设计version字段的业务，需要先补版本机制，不能假称已有乐观锁。

消息Key、委派动作ID和业务写入动作ID各有用途。根任务中的“保存行程”和“创建求助”不能共用一个无法区分命令的Key。写入去重至少绑定老人、tool、actionId和规范化参数摘要，保留期不得短于任务可恢复期；开发期可先按7天配置，外部业务另定更长周期。UNKNOWN先核查，不自动重新产生同一副作用。

### 动作标识不交给模型自由生成

首批由P2保存计划步骤stepId及准备去重标识prepareKey；Agent程序只引用这些标识。A1可以提出业务步骤草案，程序通过`POST /internal/agent/v3/tasks/{id}/steps`登记，P2返回planVersion、stepId、prepareKey；模型不接触prepareKey。

步骤登记请求的requestKey由Agent程序在发送前写入持久调用收据，同一次登记重试沿用原值。若Agent重启后本地收据不可用，先向P2读取已有planSteps；无法确定是否已登记就暂停核查，不能换Key盲目创建。P2按taskId+登记requestKey去重。

同一步骤的tool、参数、确认范围被冻结；改需求创建新planVersion/stepId并记录supersedesActionId，旧步骤失效。action.prepare按taskId+stepId+参数摘要返回同一actionId，参数不符409。P2再按actionId分配/保存业务幂等键，向外部服务使用同一个稳定标识。恢复不因attempt或invocationId变化而换掉已执行业务动作ID。

context.planSteps回传已有步骤及当前状态；context.actionLedger回传PREPARED、NOT_STARTED、RUNNING、SUCCEEDED、FAILED、UNKNOWN全部状态，而非只回成功效果。每项至少包含stepId、actionId、tool、argsDigest、confirmationId、executionStatus、effectId、businessRef、externalStatus、lastError、retryPolicy。敏感完整参数按权限读取，不能默认把所有参数写进模型提示。

Agent程序先核查RUNNING/UNKNOWN，再决定剩余步骤；模型只参与业务解释，不决定一个未知外部操作是不是可以重做。步骤登记、准备、确认和执行各有去重边界，不能只用根任务ID充当所有动作的Key。

## 八、共享长期记忆怎么用

### 1. 先分清四类信息

| 类型 | 例子 | 处理方法 |
|---|---|---|
| 本次临时情况 | 今天膝盖有点累 | 放当前任务上下文；默认不写成永久偏好 |
| 长期偏好 | 我平常更喜欢短时文化活动 | 形成候选，确认后保存 |
| 业务事实 | 已报名、求助已受理 | 查P2业务记录，不由模型记忆决定 |
| 授权状态 | 家属能不能看位置 | 查实时权限，不写成可代替授权的记忆 |

### 2. 公共能力，不新增强制memory意图

A1/A2/A3在被授权任务内均可调用memory.search，查询内容由任务目的、领域、敏感级别和当前授权共同过滤。A3负责检索和冲突策略，P2负责身份、存储、确认与访问限制。不得让Agent直接连库查询全部老人记忆。

拟开放工具：

| 工具 | 做什么 | 谁可调 | 是否写入及确认 |
|---|---|---|---|
| memory.search | 按目的检索可用记忆 | A1/A2/A3，按任务范围 | 只读，不另确认；敏感资料需已有明确授权 |
| memory.candidate.create | 提交待确认偏好或经历 | A1/A2/A3 | 只存候选，不代表长期生效 |
| memory.candidate.review | A3提出重复/冲突及处理建议 | A3 | 只写审核建议，交A1准备确认，不能代替老人决定 |
| memory.change | 按已保存候选和审核版本准备一项记忆变更 | 仅A1 | 这是需本人确认的受控动作；参数只能引用ID和版本，不能由A1改写记忆正文或扩大领域 |
| confirmation.prepare | 准备记忆新增/纠正/删除确认 | A1或P2本人页面 | 生成绑定操作，不直接写入有效记忆 |
| memory.apply | P2内部执行已确认的memory.change | 仅P2确认执行器 | 内部执行器，不是Agent可调用工具 |

本人查看`GET /api/v3/agent/memories?limit=20&cursor=...`；查看详情`GET /api/v3/agent/memories/{id}`。纠正/删除从`POST /api/v3/agent/memories/{id}/change-requests`准备确认，正文明确operation、expectedVersion及newContent（仅更新时）。不提供Agent自报confirmed即可写入的接口。

### A3审核记忆以后，具体交给谁

首批固定采用“A3给建议 → A1准备确认 → P2执行”，不允许A3或A2准备记忆新增、修改、删除或扩大范围的确认。子任务通用WAIT_CONFIRMATION只用于该Agent已经登记允许的普通领域业务，不能借此绕过记忆限制。

A3完成候选审核后，返回MEMORY_REVIEW类型结果，payload包含candidateId、candidateVersion、reviewId、reviewVersion、recommendation（ADD/MERGE/REPLACE/KEEP/REJECT）、conflictMemoryRefs、proposedDomains、needsUserConfirmation、explanation；不包含伪造的confirmationId。候选及审核完整对象先由P2存储，A1从dependencyResults或P2查询取得。

A1读取建议，若需确认，通过已登记的memory.change动作准备，参数只引用candidateId/candidateVersion、reviewId/reviewVersion和具体operation；对于改删还带目标memoryId/version。P2从已保存对象恢复完整内容、领域及敏感级别，再生成ownerTaskId为A1当前任务的确认。A1不能在请求里自行改content、value或扩展domains；想改就先重新产生候选和审核版本。

`memory.change`的首批动作Schema名为`MemoryChangeArgs`：必须提供operation、candidateId、candidateVersion、reviewId、reviewVersion；operation仅ADD、MERGE、REPLACE。MERGE/REPLACE还必须提供targetMemoryId和targetMemoryVersion，ADD不得带目标记忆字段。KEEP/REJECT是审核结论，不是写入操作，不进入memory.change。Schema在联调包中给出；P2仍需校验候选与审核属于同一老人、仍有效且版本匹配，确认后由内部memory.apply执行。

用户决定后，P2检查候选、审核、旧记忆和权限版本，执行或拒绝，之后恢复A1。A3审核子任务已经结束，不因用户点击同意而重新执行A3来重复生成候选。确需重新审核时，A1建立新的有明确关联的子任务。普通文化报名确认仍按子任务ownerTaskId恢复，不与记忆确认混用。

### memory.search完整约定

走第六节的普通工具入口；taskId、stepId、actionId和凭证仍必需。下面展示input里的工具内容：

```json
{
  "tool": "memory.search",
  "args": {
    "purpose": "为当前老人安排短时文化活动",
    "query": "步行时长、活动偏好",
    "domains": [
      "tourism",
      "culture"
    ],
    "limit": 5,
    "maxContentChars": 2000
  },
  "confirmationId": null
}
```

purpose非空最多500字符，query非空最多1000字符；domains为登记领域数组，最多3项，必须在任务授权范围内。limit默认5、范围1～10；maxContentChars默认2000、范围200～4000。各条content最多1000字符，合计按Unicode码点计数，不把来源及控制字段算进正文额度；候选条目放不下就跳过并标truncated，不默默切断一条记忆改变语义。purpose只说明用途，不能用一句话扩大权限。

工具响应data.result完整示例：

```json
{
  "readStatus": "AVAILABLE",
  "memoryRevision": 12,
  "authorizationRevision": 4,
  "retrievedAt": "2026-10-29T02:00:00Z",
  "items": [
    {
      "memoryId": "memory-001",
      "version": 2,
      "category": "LONG_TERM_PREFERENCE",
      "key": "activity.preferredDurationMin",
      "content": "平时更喜欢一小时以内的文化活动",
      "value": 60,
      "domains": [
        "tourism",
        "culture",
        "community"
      ],
      "sensitivity": "GENERAL",
      "state": "ACTIVE",
      "sourceRefs": [
        {
          "type": "USER_MESSAGE",
          "id": "msg-preference-001"
        }
      ],
      "confirmedAt": "2026-10-28T02:00:00Z",
      "updatedAt": "2026-10-28T02:00:00Z",
      "expiresAt": null
    }
  ],
  "returnedContentChars": 15,
  "truncated": false
}
```

returnedContentChars由P2按上述规则计算，不能写死。读到的value保留原类型，不能把数字60当作60小时。当前用户明确的新要求优先于旧偏好，但不自动覆盖长期记录。

| 情况 | 怎样返回 | A1怎样处理 |
|---|---|---|
| 有授权范围内的有效记忆 | HTTP200/OK，readStatus=AVAILABLE | 按来源和任务目的使用 |
| 没有匹配的有效记忆 | HTTP200/OK，readStatus=EMPTY、items=[] | 说明未取得偏好，必要时追问 |
| 请求领域或敏感范围越权 | HTTP403/FORBIDDEN | 不缩写提示词绕过授权，也不泄漏隐藏记忆是否存在 |
| 只有尚未确认候选 | 正常检索仍EMPTY或返回其他ACTIVE项 | 不把候选当长期事实；候选在本人确认流程单独查 |
| 检索服务不可用 | HTTP503/CAPABILITY_UNAVAILABLE、data=null | 可按无个性化方式降级并说明，不能声称老人没有偏好 |

### 当前调用的回复也要检查，不只检查下一轮

P2登记本轮实际读取的memoryId/version、memoryRevision、authorizationRevision和涉及字段，组成服务端readSet。Agent在响应里提供usedMemoryRefs用于解释，但不能用漏报来逃过检查；最终检查按P2真实读取集合进行。

回复、结构化卡片或待确认操作落地之前，再核对readSet与实时授权/记忆状态。若调用期间发生删除、纠正或撤权，本轮依赖结果不得返回或提交，应取消旧调用结果、清理上下文并在有效预算内新开一轮；无法安全重做就给出受控提示。首批可保守地在相关revision变化时整轮重算，不要求先实现精确依赖分析。

若已执行写入，其事实仍在effects，不因丢弃回复而丢账。P2重新组织不含失效资料的状态说明。已显示给用户的历史内容无法物理“追回”，但再次读取历史时应按当前策略遮蔽敏感信息，并阻止继续传给模型；具体历史脱敏规则需P1/P2共同确认。

### 恢复上下文也携带依赖，不只检查新检索

P2每次向Agent提供history、dependencyResults、已有reply/results、任务摘要、候选任务或completedEffects前，都按当前老人权限和记忆状态重新过滤。最初的工具读取记录、子任务派生结果和已有卡片要保存服务端provenance，至少能追到memoryId/version、memoryRevision、authorizationRevision及来源对象。

恢复时把这些内容的依赖合并进当前调用readSet；即使本轮没有memory.search，也必须在最终回复/卡片/确认落地前重新检查。不能因为内容是“上次生成的文字”就失去来源关系。Agent回传usedMemoryRefs只是补充，不替代服务端依赖账本。

无法可靠拆掉失效敏感内容时，整条历史/子结果/卡片标STALE并停止注入，不让模型根据残缺内容推测；必要时重新取得授权资料或重新计算。保留真实业务操作ID和已执行事实，可用不含敏感内容的摘要交付，不能因过滤丢失动作账本。父A1与子Agent之间仍按各自权限过滤。

模型本地历史只作临时计算缓存，不是权威档案或任务记录；收到恢复调用时以P2提供的过滤上下文为准。缓存无法清理或无法保证未使用失效资料时，取消旧调用并新建干净调用，不继续复用原模型会话。

### 4. 删除以后不能继续被用

P2标记删除后，所有记忆查询立即过滤；同一事务递增该老人的memoryRevision。检索缓存和向量索引异步删除，但查询结果返回前必须核对当前revision和状态，不能因索引还没删而继续暴露。

进行中的任务在下一次调用前清掉过期记忆上下文；模型回复若依赖已撤销范围则废弃并重新处理。已发送给外部模型的内容无法通过本地删库追回，需要按所选模型服务的数据保留约定处理，不承诺“删除后外部一定零留存”。

### 区分业务工具与Agent内部处理

fraud.analyze是A1内部模型/分析能力，由A1程序调用配置的模型并生成风险结果，不是“P2收到fraud.analyze后再调用A1”的工具。P2负责附件授权、资料查询、协同业务和结果结构校验，不能声称格式校验等于诈骗事实认定。

同样，需求拆解、领域推理、结果整合、候选偏好提取属于Agent能力；查业务数据、保存、报名、发送通知及执行确认属于P2业务工具。A3的检索算法可有独立内部服务，但对Agent的记忆访问仍经P2受控入口。工具注册表注明kind=BUSINESS_TOOL或AGENT_INTERNAL；只有前者可进入P2 tools入口，后者统计为模型/内部处理耗时，不允许形成递归回调。

## 十、图片、附件和攻略链接

附件上传接口：`POST /api/v3/agent/attachments`，multipart上传file，附带purpose（fraud_analysis或travel_reference），返回attachmentId、mimeType、sizeBytes、state、expiresAt。需要先完成所有权和内容检查，只有READY附件才能随消息传入。

首批建议只收JPEG、PNG、WebP：每个最多10MiB，每条消息最多4个，总像素最多2000万；后端验证真实类型、解析后尺寸和解码资源限制，不接受SVG、可执行文件、压缩包或通过改后缀绕过的文件。元数据先移除，检查未通过不发给模型。GIF、PDF、音频附件以后单独定义，现有语音接口不变。

文件归属于当前老人，不使用可猜路径。Agent凭任务权限向P2读取附件，由受控网关按模型接口需要传输字节或签发短时、单附件访问凭证；不提供任意本地路径和长期公开URL。模型服务商不能回调本机127.0.0.1，必须选择可受控访问的部署或直接字节上传方式。

默认附件24小时过期，短时访问凭证建议60秒。本人删除`DELETE /api/v3/agent/attachments/{id}`；立刻禁止新读取，已进行外发不保证可追回。任务超过附件有效期后，要求重新上传，不悄悄恢复已删除文件。原图不默认写入长期记忆。

攻略链接首批默认不开自动抓取。以后开启需单独link.import入口和域名白名单，只允许HTTPS，检查DNS和每次重定向，拒绝本机、内网、云元数据地址及特殊端口；限制大小、时间，不绕登录或访问控制。失败则让用户粘贴正文或上传截图，不宣称已读完链接。

## 十一、超时、凭证、并发和事件

### 1. 先统一计时口径，再测学校模型

当前选用的模型需在实际接入环境测量耗时。协议不把“模型60秒”“凭证90秒”等旧建议写成固定值。连接、首段、模型总时限、Agent总时限和任务预算是不同配置。

| 配置/指标 | 如何计时 | 谁控制 |
|---|---|---|
| modelConnectTimeout | 一次模型请求建立连接的最长等待 | Agent模型客户端/模型网关 |
| modelFirstChunkTimeout | 请求发出后到第一个有效输出片段；只连接成功不算首段 | Agent模型客户端/模型网关 |
| modelTotalTimeout | 该次模型请求发出到完整响应，包含首段等待 | Agent模型客户端/模型网关 |
| agentInvocationTimeout | P2派发一次Agent调用到收到完整结果；包含该轮多次模型、工具等待和本地处理 | P2网关与Agent共同遵守deadlineAt |
| toolTimeout | 每个业务工具独立上限，外部结果未知时另行核查 | P2工具注册配置 |
| childActiveBudget | 该子任务所有有效执行区间的累计预算 | P2任务调度器 |
| rootActiveBudget | 根任务与后代所有执行区间的时间并集，平行子任务重叠部分只算一次 | P2任务调度器 |
| rootAbsoluteExpiry | 从根任务创建开始的绝对墙钟上限，排队和所有等待也包含在内 | P2任务存储 |

“执行区间”指实际Agent调用或独立业务执行正在运行的时间。排队、WAITING_INPUT、WAITING_CONFIRMATION本身不占该任务处理预算和模型并发；若后代仍在实际执行，其执行时间仍按并集计入根任务；WAITING_DEPENDENCIES只有后代在实际执行时计入根任务执行区间，全部子任务排队时不计处理预算。父Agent等待子任务应结束本轮调用释放执行位，不保持HTTP连接空等。

另记录resourceDuration：根任务所有模型、Agent和工具实际消耗时长的累加，用于成本与容量统计，不与rootActiveBudget混为一谈。执行区间超预算后停止新动作，已发出的外部操作仍核查。时钟采用服务端单调时钟计算耗时，持久化起止点用于恢复，不能信Agent上报的elapsed来扩大额度。

待实测的配置包括模型连接/首段/总时限、Agent总时限、凭证租期、子任务预算和根任务处理预算。根任务绝对存活24小时、确认10分钟、本人最多2个运行根任务、一次响应1MiB，仍只是开发期建议。等待输入最多到绝对expiresAt；确认过期不自动同意，按前述规则重新准备。

全局模型并发必须有共享控制。建议部署负责人提供统一模型网关或共享模型并发租约，各Agent每次模型请求都申请，结束释放；三个Agent各自设上限不能宣称平台全局限流。P2的Agent调用并发与模型请求并发分别统计。共享控制由谁维护、能否限制直连，冻结第一批前明确；未接入共享控制时仅标注“各服务局部限流”，不承诺全局硬限制。

Agent每次请求把剩余deadline传给模型/工具客户端，子请求超时不得晚于本轮调用截止时间。取消需中止能中止的本地请求；无法中止的外部动作进入核查，不把断开连接当成外部撤销。

### 一次调用丢响应或进程重启，P2怎么处理

建议各Agent提供`GET /internal/v3/invocations/{invocationId}`，由P2用对应服务密钥查询。存在时HTTP200，data.status取RECEIVED、RUNNING、FINISHED、FAILED，并提供已完成响应摘要/可重取结果；没有收据返回HTTP404/NOT_FOUND。Agent程序在开始处理前保存调用收据，同invocationId重复送达不能并行执行第二次；具体收据存储由各Agent实现，不能只保存在模型对话里。

P2调用超时先登记本轮UNKNOWN并查询调用收据、步骤与动作账本；能取回完成响应就验收，仍在运行则先请求取消并核查副作用。明确未接收/未执行且允许恢复时，才由调度器登记新的attempt和invocationId。旧invocationId、旧凭证及旧恢复代次失效，迟到响应只归档，不覆盖当前结果。

若无法判断是否已经写入，不自动重派整段任务；先按actionId查实际业务。人工/用户可看到“结果核查中”，不把UNKNOWN写成失败后重建。完成核查后，从已保存planSteps/actionLedger恢复未完成步骤，沿用原业务动作标识，不以新的invocationId生成全新业务写入。

进度上报是轻量快照更新：带invocationId和progressSeq，按当前有效调用与递增序号去重；过期上报忽略/返回冲突，不能让进度版本冲突撤销合法的最终回复。最终回复按本轮交付baseTaskVersion记录及有效invocationId验收，另检查授权/记忆readSet，普通taskVersion增长不单独判它失效。

### 2. 凭证绑定什么

P2内部保存或签名绑定：userId、conversationId、taskId、invocationId、callerAgent、allowedTools、allowedDomains、attachmentScope、expiresAt及撤销版本。凭证短时有效，租期待真实调用耗时测试后配置，权限取任务授权与Agent工具白名单的交集；不把旧版90秒建议当成固定承诺。

有效任务需要继续调用时，由P2在下一轮调用重新签发；必要的续签入口只接受当前Agent服务身份和仍有效调用，不允许靠过期凭证自行延长。取消、任务过期、授权撤销立即禁止新动作。子任务取得新凭证，不复用父密钥或继承全部资料。

Agent上报处理阶段可用`POST /internal/agent/v3/tasks/{id}/progress`，只允许本次invocationId提交登记的phase、简短说明和递增progressSeq。P2不接受它伪造业务成功，终态由持久执行结果和本轮返回共同校验。

### 3. SSE为可选第二步，不阻塞第一批实现

后续可增加`GET /api/v3/agent/tasks/{id}/events`，鉴权与查任务相同。首批使用轮询任务查询。

| 事件 | 表示什么 |
|---|---|
| task.phase | 实际处理阶段变化 |
| reply.delta | 尚未定稿的模型文字片段，不能当作已执行凭证 |
| result.ready | 一项通过校验的业务卡片可读取 |
| confirmation.required | 存在可从P2查询的待确认操作 |
| task.failed | 任务失败，带可公开的原因 |
| task.cancelled | 已停止后续执行 |
| task.finished | SUCCEEDED或PARTIALLY_SUCCEEDED |
| task.expired | 任务过期 |
| stream.end | 当前事件连接结束，不等于业务成功 |

每条事件有eventId、taskId、taskVersion、occurredAt、payload。业务事件持久保存并支持Last-Event-ID重放，客户端按eventId去重；临时文字增量可不重放。游标超出保留范围时，先GET任务快照再从新游标继续。心跳建议15秒，无业务含义。首批关闭reply.delta，正式回复先完成权限、记忆读集和内容检查再展示。以后开放文字流需要逐段校验当前授权并能立即停止；已显示/已播报的片段无法追回，不能把最终落地检查宣传为能撤回已经输出的内容。

原生EventSource不能方便地添加当前mock身份头；P1首批使用fetch流或轮询。不能为兼容SSE把密钥或长期身份信息放URL。断流后先查任务，不能重新提交相同需求创建另一个任务。

## 十二、三个完整场景怎么跑

### 场景一：文化活动，随后修改，再确认保存

1. 用户：“明天安排一个轻松的文化活动。”P2建conv-001/msg-001/task-001。
2. A1查当前授权资料，经P2委派A3找文化活动；没有真实资料时活动卡标DEMO或UNAVAILABLE。
3. A1拿到结构化结果，创建行程草案，不报名、不共享。草案引用具体draftId/draftVersion。
4. 用户：“时间再短一点，控制在一小时内。”前端发同conversationId及continueTaskId；P2分配新messageId，A1基于已保存草案版本处理。终态旧任务则创建关联新任务，不能强行恢复终态。
5. A1准备保存操作，P2生成confirm-001；P1显示具体行程和“不报名、不共享”的范围。
6. 用户点击同意，P2核查版本并保存，effects记录真实itineraryId/version。A1恢复并解释结果。
7. 用户说“以后都尽量一小时内”，才另外生成长期偏好候选和单独确认。拒绝记忆不影响已经保存的行程。

```json
}
```

riskLevel暂定UNKNOWN、LOW、MEDIUM、HIGH；LOW也不能解释为安全保证。是否联系家属是另一个需授权的动作，不在分析成功时自动发送通知。

### 场景三：求助已创建，但最后回复失败

1. 用户明确发起求助，P2保留原始动作Key，A2通过受控工具创建。
2. help.create返回真实helpId，P2保存effect。通知另外记录deliveryMode和投递状态。
3. A1最终组织回复时超时。任务可FAILED或PARTIALLY_SUCCEEDED，但effects仍显示HELP创建成功。
4. P1查询任务，显示“求助记录已创建，回复生成失败”；通知为MOCK就明确未真实触达。
5. 用户重试时查询同一动作和helpId，不创建第二条求助。“不用通知了”只取消尚未执行的通知动作；已发出的通知无法假称撤回。

## 十三、安全、错误和运行规则

保留v2的独立服务密钥、TLS/本机限制、X-Trace-Id、文本有效性和工具记录校验。密钥、地址、超时由服务配置提供，不放模型提示词或前端代码；服务至少提供不泄露数据的GET /health。

用户文本、攻略、图片OCR及检索内容都是待处理资料，其中的指令不能改变系统角色、工具白名单、确认要求或访问范围。P2不接受Agent传来的“我是管理员”“用户已同意”等文字作为权限证明。

日志记录taskId、actionId、工具名、状态和耗时，默认不记原文、原图、完整档案、密钥或凭证。排查需要临时记录内容时必须有明确范围和自动清理期限。健康和照护建议由A2负责专业边界，反诈骗由A1负责证据和不确定性，长期偏好推断由A3负责来源及冲突，P2格式通过不等于内容可靠。

沿用现有INVALID_ARGUMENT、UNAUTHORIZED、FORBIDDEN、NOT_FOUND、CONFLICT、UPSTREAM_ERROR、UPSTREAM_TIMEOUT等业务码。建议补充：

| HTTP | code | 含义 |
|---|---|---|
| 400 | UNSUPPORTED_PROTOCOL_VERSION | 版本不支持 |
| 409 | STALE_VERSION | 任务或业务对象已更新，重新读取 |
| 409 | CONFIRMATION_REQUIRED | 不能直接执行，需要本人确认 |
| 409 | CONFIRMATION_EXPIRED | 待确认操作已过期 |
| 409 | QUESTION_NOT_PENDING | 问题已回答、版本过时或已失效 |
| 409 | INPUT_REQUEST_ID_CONFLICT | 新问题ID已经分配给其他问题/归属，或重放时同ID内容不一致 |
| 409 | TASK_NOT_RUNNABLE | 任务已取消、结束或过期，不接受执行 |
| 429 | RATE_LIMITED | 达到并发或调用额度，按服务建议等待 |
| 503 | CAPABILITY_UNAVAILABLE | 已登记能力尚未接入或不可用 |

这些新增错误码目前未实现。所有v3请求响应使用JSON UTF-8，响应头回传X-Agent-Protocol-Version: 3.0和X-Trace-Id；上传和SSE按各自Content-Type。

一次GET任务成功可HTTP200/OK，同时data.status=FAILED；这是“成功查到了失败任务”，不是接口自己失败。任务error固定为code、message、retryable；retryable只表示可考虑恢复，不授权自动重复写入。

## 十四、版本切换和开发顺序

### 升级顺序

1. 现有v2代码作为迁移来源，不再作为新功能的开发目标。P2按本文把所有公开业务路由和Agent接口改为v3.0。
2. P2提供v3任务、查询、确认和业务工具mock；A1提供总调度mock；A2/A3按子任务模板提供可测试响应。
3. 先完成任务与协作，再完成确认与恢复，最后联调共享记忆。每一步都用联调包中的Schema和样例核对格式，并对状态、权限、幂等和竞态做服务测试。
4. 前端、P2、A1、A2、A3和Postman测试集合统一切到v3.0路径与字段。不要让同一个客户端按业务功能在v2和v3之间切换。
5. 全部调用方和接口通过验收后，以一个切换点启用v3.0并移除旧路由；不长期并行维护v2/v3。切换日期由项目负责人安排。

同一主版本新增可选响应字段，接收方允许忽略；新增请求字段仍须接收方先支持。删除、改名、改变语义或执行方式升级主版本。结构化卡片另有schemaVersion，不和整体协议版本混为一谈。

### 第一批先做到哪里

按三步分别验收，不等全部领域做完：

1. **任务与协作**：建任务、A1委派、子结果回传、普通追问WAITING_INPUT、明确指代和A1整合。A2/A3可先给固定测试案例，必须标DEMO。
2. **确认与恢复**：动作准备、父子任务确认、同意/拒绝/过期、实际执行、失败/未知查询、回复丢失后的安全恢复。
3. **共享记忆**：候选、确认、授权检索、跨领域使用、纠正删除及当前调用落地前失效检查。领域内容先用明确标记的演示数据，不要求此时接完全部第三方。

SSE、真实报名、复杂多日行程、更多领域工具按后续批次开发。第一批也可再拆成任务/协作、确认/写入、记忆三次交付，减少多人同时改所有接口的风险。

### 首批实现要求

- 按本文和配套Schema实现控制层；Schema不能校验的权限、状态、版本、幂等和串行恢复由运行服务验收。
- 调用收据持久化、Agent取消入口和子任务恢复要有明确实现负责人；模型耗时和并发额度以部署环境实测后配置。
- 自动任务转交、SSE、真实报名、复杂行程和新增外部通知不属于首批范围。A2/A3可用明确标注DEMO的固定结果联调。
- 每个领域工具由对应Agent负责人和P2共同补齐参数、结果、权限、确认、幂等及错误规则；P2提供受控执行能力，不代替Agent实现领域逻辑。

## 十五、共同验收清单

- 同一会话能理解“刚才那个”“第二天”，不明确时进入WAITING_INPUT；补充后恢复同一任务，终态修改另建relatedTaskId任务。
- 未带continueTaskId时A1收到候选列表并追问，P1明确携带continueTaskId；首批不接受自动转交。
- 必选/可选子任务失败、多个结果同时到达、子任务待确认/待输入均按规则恢复，不同时启动两个父调用。
- 子任务问题经A1统一展示，答案只回原问题所属子任务；版本过期、重复回答、根任务取消正确拒绝。
- A3记忆审核只返回候选与建议；A1不改候选内容就能准备确认，A3不能自行准备记忆确认。
- A2/A3先后出现不同确认时均能提示，不重复弹旧项，不合并成一次无限范围授权。
- 一个需求可调用多个领域，子任务部分失败时保留成功部分，不能循环调用。
- 文旅、反诈骗均有文字/结构化结果，演示资料和待核实内容明确。
- 同意、拒绝、取消、过期及重复点击不导致越权或重复写入；子任务确认先恢复所属子任务，再整合父结果。
- EXECUTION_FAILED与EXECUTION_UNKNOWN页面表现不同，未知结果核查前不能自动重试。
- 已确认偏好能在授权领域使用；纠正、删除或撤权后，旧缓存、后续任务和当前尚未落地的回复都不能继续用失效内容。
- memory.search区分EMPTY、403和503，并遵守条数、内容量及敏感范围限制。
- 页面断开后可查询恢复；任务取消、超时不抹去已执行事实。
- 密钥错误、跨用户/跨任务凭证、过期凭证、未开放工具和伪造执行记录被拒绝。
- 截图/攻略中的指令不能扩大工具权限；非法URL和附件被拒绝。
- 工具写入成功但模型回复失败时，能查到真实业务ID和状态，重试不重复办理；重启后能找回步骤、动作和调用收据。
- 模型连接、首段、总响应和Agent总耗时分别统计；并行子任务预算按并集计算，成本时长按累加记录。
- 任务完成、业务提交、通知发送、接单、实际办结分别显示，不能统一写成“已完成”。

## 配套控制层格式与取消约定

[v3.0联调包](agent-v3-r3/README.md)包含control.schema.json、examples.json和本地校验脚本。它定义首批控制层字段；领域内部结构仍按已登记工具Schema校验，未登记的能力不开放。

首批演示写入使用demo.action，仅用于独立联调测试数据，不创建真实报名、支付或通知；生产环境不得开放该工具。它尚未实现，样例不代表已有可运行服务。

P2到Agent的取消入口为POST /internal/v3/invocations/{invocationId}/cancel，正文包含protocolVersion、invocationId、cancelRequestId、reason。cancelRequestId由P2生成并保存，相同ID重复提交返回同一控制请求，不重复启动取消流程。P2先使旧凭证/调用不可再产生新动作，再发取消。

返回CANCEL_REQUESTED只说明已接受取消；最终查询调用收据，status可新增CANCEL_REQUESTED/CANCELLED。CANCELLED表示Agent不再发起后续操作，不承诺已经发出的外部请求撤回；reconciliationRequired=true时P2继续查动作账本。迟到FINISHED结果因invocation已失效不能覆盖当前任务，但实际effects必须保留。没有调用收据返回404/NOT_FOUND，不把收据丢失直接解释为确定没有副作用。

联调完成前不在现有v2服务上启用这些端点。调用方使用v3接口前，须确保对应服务已部署并通过联调。
